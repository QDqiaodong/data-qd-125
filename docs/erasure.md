# 用户擦除 v3（erase）与发布代际栅栏

在 SQLite 增量管道（[incremental.md](incremental.md)）与差分隐私发布
（[privacy.md](privacy.md)）之上新增用户擦除命令。旧全量 CLI 行为不变；
`apply`/`export`/`privacy-release` 的既有契约保持兼容，变更均为加法式迁移。

## 命令与请求契约

```sh
python -m visit_attribution.cli erase --db run/store.db --request erase.json
```

请求文件沿用受限 JSON（≤8MB、拒绝重复键与非有限数值），字段严格为：

```json
{
  "request_id": "ER-2026-001",
  "users": ["user-a", "user-b"]
}
```

- `request_id`：非空白标识（≤128 字符、无控制字符），擦除凭据主键。
- `users`：非空数组（≤10000 项），每项为与事件 `user` 同规范的非空白标识；
  数组内重复按一个用户处理。标识在库内从不落盘——参与校验后立即转为
  **UTF-8 字节的 SHA256**，后续全部以哈希比较与存储。
- 规范集合 = `sorted({sha256(u) for u in users})`；规范哈希随请求 ID 存为凭据。

## 擦除语义（单源事务）

一次 `erase` 在源库**单条 `BEGIN IMMEDIATE` 事务**内完成，提交后：

- 删除目标用户的**全部** `events` 行——包括 `active=0` 的未来事件；
- 删除其全部物化行：`m_sessions`、`m_session_events`、`m_conversions`；
- 写入永久墓碑 `tombstones(user_sha256, request_id)`，只存哈希，不存标识；
- 写入擦除凭据 `erasures(request_id, spec_sha256, user_count, unknown_users)`；
- **保留** `batches` 批次凭据、`meta` 水位与 gap/lookback、其他用户全部数据。

会话/转化物化按 `user` 分区，删除用户不需要重算任何其他用户，因此事务内
没有跨用户窗口计算，独占窗口只覆盖按用户索引的范围 DELETE。

未知用户（库中无任何事件）同样写墓碑并计入 `unknown_users`：擦除请求对
"从未出现的标识"也产生永久封禁效果。CLI 摘要示例：

```json
{"request_id":"ER-2026-001","replayed":false,"erased_users":2,"unknown_users":1,
 "tombstones_written":3,"tombstones_total":3,"generation":4}
```

## 幂等与冲突

- **同 ID 同规范集合**：直接返回 `replayed=true`，不删任何行、不重复写墓碑、
  不推进代际；用户顺序不同、重复项不影响规范集合，视为同一请求。
- **同 ID 异参**（用户集不同）：拒绝，不写任何内容。
- **不同请求 ID 引用已被其他请求擦除的用户**：整批拒绝（墓碑永久且只归属
  一个擦除请求），库内不产生部分删除。

## 再入库封禁（apply 遇墓碑整批拒绝）

`apply` 在批次重放判定之后、写入之前检查全部事件的用户哈希：任一用户已在
`tombstones` 中，整批拒绝（退出码 2，错误信息只含哈希不含标识），不写事件、
不写批次凭据、不推进水位、不推进代际。未知用户的墓碑因此与已知用户等效封禁。
已成功批次的同字节重放仍为无副作用 no-op（墓碑检查只作用于新批次）。

## 隐私账本：历史不变，新发布不含已删用户

- 账本是独立 SQLite 文件，擦除**不触碰**账本：历史发布的载荷字节、噪声采样、
  已花费与剩余预算全部保持原样。已提交的 `release_id` 重放仍返回**原字节**，
  不重读源库、不重新采样、不二次扣费。
- 擦除后任何**新** `release_id` 只能读到擦除后的源快照，已删用户不可能再出现在
  新发布的真实计数中（噪声机制本身不变）。
- 源库对发布路径始终 `mode=ro` 只读打开，发布前后源库文件字节一致。

## 并发设计：为什么是代际栅栏而不是长锁

`apply`、`erase`、`privacy-release` 三命令允许跨进程并发。需求要求在
"长时共享/独占锁" 与 "代际栅栏" 之间比较阻塞与重算代价后选一实现，
且不得一刀切拒绝并发。两种纯方案的对比：

| 维度 | 纯长锁（发布持共享锁全程，擦除持独占锁全程） | 纯代际栅栏（代际版本号+复检） |
| --- | --- | --- |
| 阻塞范围 | 发布的噪声采样与账本提交全程阻塞写者；擦除大用户集时全部 apply/export 排队 | 读写互不阻塞，仅冲突方重试 |
| 跨库死锁 | 源库与账本是两个独立 SQLite，持源锁再等账本锁存在锁序反转风险 | 账本事务内不持有源写锁，无跨库锁序 |
| 失败代价 | 锁等待超时（busy_timeout）后整操作失败 | 快照作废，重读一次源快照（只读聚合，无写入回滚） |
| 正确性缺口 | 无（锁本身可线性化） | 复检与提交之间仍有微小 check-then-act 窗口 |

**本实现采用混合方案**，取两者之长：

1. 源库 `meta.write_generation` 为代际计数器，每次**提交成功**的 `apply`/`erase`
   加一；重放与拒绝不加。
2. 发布先在只读短事务内取 `(快照, generation)`，随后开启账本 `BEGIN IMMEDIATE`，
   并在账本事务内重新以只读事务打开源库复检代际：
   - 代际变化 → 释放读连接、回滚账本事务，报 `source changed since snapshot`，
     **不扣费、不写载荷、不产输出文件**，调用方用同一请求重试即可；
   - 代际一致 → 在该只读事务（共享锁）保持打开期间完成账本扣费与提交。
3. 复检的共享锁持续到账本提交：擦除/apply 的 `BEGIN IMMEDIATE` 在此期间拿不到
   独占提交锁，只能在 `busy_timeout`（5s）内等待——**有界阻塞、可重试，而非拒绝**。
   这把纯栅栏的残余窗口关闭，使顺序只能是两种干净线性化之一：
   - 发布先：发布按旧快照扣费成功，擦除随后提交；已提交 ID 永久返回原字节。
   - 擦除先：发布复检发现代际前进而中止，不扣费；重试读到擦除后快照。

代价分析：无冲突时发布仅多一次索引化单行 `meta` 读取；冲突时失败方损失一次
只读快照聚合（源库只读、无脏写回滚），重试成功后总扣费恰好一次。不存在为了
规避并发而拒绝全部请求的路径。

## 崩溃与中断

- 擦除的全部删除/墓碑/凭据/代际更新在一个源事务内，默认 rollback journal 保证
  崩溃原子性：提交前崩溃 → 重启后自动回滚，无半删、无墓碑残留，重试正常完成；
  提交后崩溃 → 删除持久，重试同一请求走幂等重放，数据不会复活。
- `VA_ERASE_FAULT_AFTER_COMMIT` 模拟提交后、返回前的故障，验证重试为重放且
  再入库仍被封禁。
- 发布侧沿用 `VA_PRIVACY_FAULT_AFTER_COMMIT`：账本提交后写文件失败保留旧文件，
  重试免费补发；被栅栏中止的发布在账本中不留任何痕迹。

## 迁移

- **源库**：`connect()` 的 `CREATE TABLE IF NOT EXISTS` 自动补建 `tombstones`、
  `erasures` 两表；旧库打开即完成加法迁移，既有行不变。`write_generation`
  缺失视为 0，首次提交成功的写操作后变为 1。
- **账本**：打开时若 `releases` 缺少 `source_generation` 列则
  `ALTER TABLE ADD COLUMN ... DEFAULT 0`，旧发布行标记为代际 0，载荷与预算不变。

## 表结构摘要（源库新增）

| 表 | 用途 |
| --- | --- |
| `tombstones` | 永久墓碑：用户 UTF-8 的 SHA256、归属擦除请求 ID、创建时间 |
| `erasures` | 擦除凭据：请求 ID、规范集合哈希、用户数、未知用户数、创建时间 |

`meta` 新增键 `write_generation`（发布代际栅栏版本号）。

## 测试

`tests/test_erase.py` 覆盖（含真实跨进程 CLI 实测）：

- 请求校验；未知用户墓碑；已知/未知混合；未来行随会话/成员/转化一并清除；
  墓碑仅存哈希且库文件字节中不含原标识；批次凭据与水位保留；
- 同请求重放无副作用（逐表快照比对）、同 ID 异参拒绝、跨请求已擦用户整批拒绝；
- apply 遇墓碑整批拒绝、已成功批次重放仍 no-op、擦后再入库封禁；
- 代际单调递增；线程内与跨进程两种方式验证擦除/apply 提交于栅栏窗口时发布
  中止且不扣费，重试成功且不多扣预算；发布持栅栏锁时擦除被阻塞而非拒绝，
  发布先提交后擦除再提交，已提交 ID 重放取原字节；
- 提交前 SIGKILL 回滚无半删、提交后故障重试为重放且不复活；
- 旧账本迁移后载荷与预算不变；源库只读字节不变；CLI 端到端与错误退出码。
